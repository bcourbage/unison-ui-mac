# Unison UI for macOS 0.10.0

Version 0.10.0 completes how a `unison <profile>` request behaves when the app is
already running. A request now carries its own command-line options to the running
instance, waits for the app when it is busy instead of being turned away, and,
when a synchronization is in progress, asks you how to handle it. Existing profiles
and settings continue to work without migration.

## Added

- **Options are delivered to the running instance.** `unison <profile> -path <dir>`
  handed to a running app opens that profile scoped to `<dir>`, exactly as the same
  command would at a fresh launch. `-include` and `-source` are carried too, with
  order, repeated options, and profile precedence preserved. How the running app
  was itself started no longer matters: each request is scoped only by its own
  options.
- **A busy app makes the request wait instead of turning it away.** If the app is
  scanning, showing reconciliation results, or finishing a previous run, it accepts
  the request and opens the profile once that work and its cleanup finish. The
  command reports that it was accepted and is waiting, and the app shows it waiting.
- **A request during a synchronization asks how to handle the sync.** When a sync
  is running, the app raises its Keep Syncing / Abort & Close / Close (let it run)
  decision for the requested profile. The command prints that a synchronization is
  running and a decision is required in the app, then waits for your choice within a
  short window: stopping the sync or letting it finish in the background opens the
  requested profile; Keep Syncing leaves the sync untouched and does not open it. No
  command ever aborts a sync or makes that choice on its own.

## Changed

- **A request to a busy app is no longer simply refused.** Earlier versions kept the
  work in progress and told you they did not start the new profile. Now the request
  waits (for a scan or cleanup) or asks you how to handle a running sync, and opens
  the profile when it can. The profile editor and a recovery/restart state still
  refuse, with a specific reason and the step to take.

## Notes

- Only one command-line request is handled at a time. A second request while one is
  waiting is refused with a clear message, and choosing a profile in the app never
  silently replaces a waiting command-line request.
- If a request cannot be confirmed (the reply was lost), the command says so and
  asks you to check the app before running it again, rather than retrying on its
  own; the original request may already have been accepted.
